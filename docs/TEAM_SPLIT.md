# Розподіл роботи на двох учасниць

Імена замініть на ваші. Розподіл зафіксуйте в GitHub Issues на початку (Зріз 0). Кожна учасниця створює власні гілки, коміти й PR; не підміняйте авторство.

## Учасниця 1 — каталог і дані (backend + пошук)
**Відповідальність:** моделі `Master`, `BeautyService`, `Booking`; `ApplicationDbContext`; індекси та зв'язки БД; `DbInitializer`; `MastersController`; каталог і сторінка профілю; фільтрація; доменні правила перевірки часу; тести правил перетину інтервалів.

**Артефакти:** Issues для моделі/схеми/каталогу/пошуку; feature-гілки; PR із кодом; короткі архітектурні рішення; тести; один або більше змістовних code review PR другої учасниці.

## Учасниця 2 — користувачі, запис та інтерфейс/якість
**Відповідальність:** `AppUser`; налаштування Identity; `AccountController`; `BookingsController`; ViewModels та валідація; Razor-сторінки й адаптивний CSS; xUnit-тести; GitHub Actions; README та тестова документація.

**Артефакти:** Issues для реєстрації/входу/запису/скасування/UI/CI; feature-гілки; PR; результати тестів; один або більше змістовних code review PR першої учасниці.

## Спільні обов'язки
- Разом узгодити вимоги та зафіксувати зони відповідальності до початку основної роботи.
- Кожна бере задачі й оновлює Issue; якщо є ризик затримки — повідомляє ДО дедлайну та погоджує нову дату.
- Кожна має щонайменше один змістовний review чужого PR; для максимального рівня B3 потрібно ≥3 результативних review на учасницю, якщо це реально в межах проєкту. Результативність — знайдена суттєва проблема/обґрунтоване покращення, реакція автора та перевірка виправлення.
- Провести демо на двох ОС, наприклад Windows і Linux/macOS. Не заявляти C0=1, доки обидва запуски не продемонстровані.
- На захисті кожна пояснює власні файли та може внести невелику зміну без допомоги іншої.
